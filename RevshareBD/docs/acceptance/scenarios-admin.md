# Сценарии приёмочной проверки — Администратор

Пошаговые сценарии для каждой админской истории. Источник историй: [`user-stories.md`](./user-stories.md) (A-01..A-13). Протокол прогона заполняется по [`run-template.md`](./run-template.md).

## Как читать

Каждый сценарий — это «предусловия → шаги → ожидаемый результат». Поле **Тип** говорит, как сценарий проверять:

- **авто** — уже закрыт pytest-тестом.
- **ручной** — проверяется в админке (браузер, /admin/..., /reports/...).
- **гибрид** — есть и авто-часть (логика), и ручная часть (визуальная сводка).

## Предусловия, общие для всех сценариев

- Подняты `revshare-web` и `revshare-worker`.
- В БД есть минимум 2 партнёра с разными состояниями (нет отчёта / сдан / подтверждён / вручную).
- Включён вход в админку, если используется сценарий A-13.
- Запущен планировщик перепроверки (если сценарий зависит от него).

## A-01. Видеть состояние отчёта

**Предусловия:** минимум 4 партнёра с разными статусами; один — «поставлен в очередь» (`dispatch`).
**Тип:** авто + ручной.

**Шаги:**
1. Создать ситуации:
   - Партнёр X: нет отчёта.
   - Партнёр Y: партнёр сдал через Telegram, не подтверждён.
   - Партнёр Z: отчёт внесён вручную админом.
   - Партнёр W: подтверждён.
2. Партнёра W поставить в очередь (`dispatch.send`) и дождаться отправки.
3. Открыть `/admin/partners` (сводка).

**Ожидаемый результат:**
- Четыре подписи в сводке: «Не сдан», «Партнёр сдал отчёт», «Отчёт добавлен админом», «Подтверждено».
- Партнёр W после постановки в очередь продолжает отображаться как «Подтверждено».

**Автотесты:** `tests/test_status_simplification.py::test_missing_when_no_report`, `::test_partner_submitted_after_bot_upload`, `::test_admin_submitted_after_manual_entry`.
**Код:** `src/revshare/store.py` — статусы; `templates/dashboard.html` — отображение.

## A-02. Фильтровать по статусу

**Предусловия:** 4+ партнёра в разных статусах.
**Тип:** ручной.

**Шаги:**
1. Открыть `/admin/partners`.
2. Применить каждый из 4 фильтров по очереди.
3. Сверить число строк в выдаче.

**Ожидаемый результат:**
- Каждый фильтр показывает только партнёров соответствующего статуса.
- Никто не пропущен (объединение фильтров = полный список).

**Код:** `templates/dashboard.html`, `src/revshare/web.py` — `GET /admin/partners?status=...`.

## A-03. Находить расхождения

**Предусловия:** отчёт без расхождений, отчёт с расхождением (например, неизвестный Location ID).
**Тип:** ручной.

**Шаги:**
1. Подготовить два отчёта (с и без расхождения).
2. Открыть `/admin/partners`.
3. Применить фильтр риска.
4. Открыть карточку проблемного партнёра.

**Ожидаемый результат:**
- В фильтре риска — только проблемный отчёт.
- В карточке — понятное описание причины.
- Старые категории расхождений **не** показываются как фильтр статуса (только риск).

**Код:** `templates/dashboard.html`, `templates/partner_edit.html`, `src/revshare/store.py` — `assess`.

## A-04. Подтверждать и отменять подтверждение

**Предусловия:** есть два отчёта — от партнёра и внесённый вручную.
**Тип:** ручной.

**Шаги:**
1. Открыть отчёт партнёра в админке, нажать «Подтвердить».
2. Проверить статус и время.
3. Нажать «Отменить подтверждение».
4. Повторить для ручного отчёта.

**Ожидаемый результат:**
- После подтверждения — «Подтверждено».
- После отмены — статус возвращается к типу подачи («Партнёр сдал отчёт» или «Отчёт добавлен админом»), а не к «Не сдан».
- Время статуса обновляется на момент подтверждения/отмены.

**Код:** `src/revshare/web.py` — `POST /reports/{id}/confirm`, `POST /reports/{id}/unconfirm`.

## A-05. Сохранять подтверждение при перепроверке

**Предусловия:** есть подтверждённый отчёт, планировщик перепроверки активен.
**Тип:** ручной + авто.

**Шаги:**
1. Подтвердить отчёт.
2. Изменить данные сверки (например, добавить/изменить строку в `reconciliation_base`).
3. Дождаться перепроверки.
4. Проверить статус.

**Ожидаемый результат:**
- Если перепроверка не нашла реальных изменений — статус остаётся «Подтверждено», время статуса не сдвигается.
- Если перепроверка нашла новое расхождение — статус остаётся «Подтверждено», но в причине появляется новое расхождение. Решение о сбросе — за админом, не автоматически.

**Автотесты:** `tests/test_revalidation.py::test_worker_revalidates_every_report`, `::test_worker_detects_status_change`. `tests/test_status_timestamp_regression.py::test_status_dates_only_change_for_submission_or_real_status_change`.
**Код:** `src/revshare/revalidation.py`, `src/revshare/store.py` — `assess` с защитой подтверждения.

## A-06. Видеть историю отчётного месяца

**Предусловия:** партнёр с одним подтверждённым отчётом и одним загруженным, но не подтверждённым файлом.
**Тип:** ручной + авто.

**Шаги:**
1. Загрузить файл без подтверждения (через Telegram или веб).
2. Открыть карточку партнёра.
3. В карточке партнёра открыть вкладку «Отчёты».
4. Выбрать месяц с подтверждённым отчётом и загруженным, но не подтверждённым файлом.
5. Проверить единую историю выбранного месяца.
6. Подтвердить файл; проверить появление версии в той же истории.

**Ожидаемый результат:**
- Отчёты показаны списком по месяцам; отдельных разделов «Отчёты» и «Черновики» нет.
- В истории месяца видны загрузка неподтверждённого файла, подтверждённые версии и остальные существующие события.
- Неподтверждённый файл **не считается** отправленной версией.
- После подтверждения файл превращается в версию в той же истории.

**Автотесты:** `tests/test_admin_drafts.py::test_admin_drafts_view_renders_rows_and_delete_button`, `::test_admin_can_delete_bot_draft`.
**Код:** `templates/partner_edit.html`, `src/revshare/store.py`, `src/revshare/web.py` — месяцы и объединённая история.

## A-07. Видеть версии

**Предусловия:** у отчёта есть минимум 2 версии (отправлено дважды, второе подтверждено).
**Тип:** ручной.

**Шаги:**
1. Открыть `/reports/{id}`.
2. Найти историю версий.
3. Сравнить каждую версию с исходным файлом.

**Ожидаемый результат:**
- В истории показаны: оборот, валюта, число клиентов, ставка, сумма к выплате — на момент отправки.
- Сохранённая ставка соответствует действовавшей на момент отправки (даже если позже её поменяли в карточке).

**Код:** `src/revshare/store.py` — `report_versions`; `templates/report.html`.

## A-08. Видеть события

**Предусловия:** один отчёт внесён вручную админом, другой — отправлен партнёром и подтверждён.
**Тип:** ручной.

**Шаги:**
1. Открыть карточки обоих отчётов.
2. Найти единую историю выбранного месяца.

**Ожидаемый результат:**
- В истории — тип действия и исполнитель (для ручного ввода — «админ»).
- Для партнёрского — «отправлено», «подтверждено», «отменено».
- Хронологический порядок.

**Код:** `src/revshare/store.py` — `report_events`; `templates/report.html`.

## A-09. Доверять времени статуса

**Предусловия:** подтверждённый отчёт, активный планировщик.
**Тип:** авто + ручной.

**Шаги:**
1. Записать текущее `status_at` у отчёта.
2. Запустить перепроверку (например, `python -m revshare.worker`).
3. Дождаться окончания.
4. Сравнить `status_at` до и после.
5. Подтвердить/отменить подтверждение; проверить обновление.

**Ожидаемый результат:**
- Если перепроверка **не** изменила состояние — `status_at` прежний.
- Если изменила (новое расхождение, ручной ввод) — `status_at` обновлено.
- При ручном действии админа — `status_at` обновлено.

**Автотесты:** `tests/test_status_timestamp_regression.py::test_status_dates_only_change_for_submission_or_real_status_change`.
**Код:** `src/revshare/store.py` — `status_at`; `src/revshare/revalidation.py`.

## A-10. Не менять чужой статус

**Предусловия:** 2 партнёра A и B; у A — подтверждённый отчёт, у B — пусто.
**Тип:** авто.

**Шаги:**
1. Зафиксировать `status` и `status_at` партнёра A.
2. Отправить отчёт партнёра B (через Telegram или вручную).
3. Сравнить данные A.

**Ожидаемый результат:**
- `status` и `status_at` партнёра A **не изменились** без причины.
- Изменения у A — только если расчёт сверки явно затронул A (например, пересечение Location ID).

**Автотесты:** `tests/test_status_timestamp_regression.py::test_conflict_does_not_change_other_partner_status`.
**Код:** `src/revshare/store.py` — `assess` (фильтр по partner_id).

## A-11. Видеть пересечения Location ID

**Предусловия:** 2 партнёра, у обоих один и тот же Location ID.
**Тип:** ручной + авто.

**Шаги:**
1. Партнёр A отправляет отчёт с Location ID `L1`.
2. Партнёр B отправляет отчёт с тем же `L1`.
3. Открыть карточки обоих.
4. Повторно отправить отчёт одного из партнёров.

**Ожидаемый результат (после согласования Q-02):**
- Расхождение «пересечение Location ID» видно в карточках вовлечённых партнёров согласно решению Q-02.
- Повторная отправка одного не стирает прежнюю причину у другого.
- Зафиксировать фактическое поведение в протоколе.

**Автотесты:** `tests/test_status_timestamp_regression.py::test_submission_does_not_erase_other_partner_cross_partner_reason`.
**Код:** `src/revshare/store.py` — пересечения.
**Открытый вопрос:** Q-02.

## A-12. Открывать историю при недоступных курсах

**Предусловия:** есть сохранённый курс за нужный месяц (или нет — повторить дважды).
**Тип:** ручной.

**Шаги:**
1. Поднять заглушку, которая возвращает ошибку на `https://.../fx` (или просто выключить интернет).
2. Открыть `/reports/{id}`.

**Ожидаемый результат:**
- Страница открывается **без зависания**.
- Курсы подставлены из кеша или резервного источника.
- Видно, какой источник использован.
- Сумма к выплате рассчитана.

**Шаг 2 (вариант без кеша):** повторить с пустым `fx_cache` за нужный месяц. Должно быть видно предупреждение, но не 5xx.

**Код:** `src/revshare/fx.py` — `fetch_month_average_rates`; `src/revshare/web.py` — рендер `/reports/{id}`.

## A-13. Открывать админку в MVP

**Предусловия:** свежий запуск сервиса, без `REVSHARE_ADMIN_AUTH`.
**Тип:** ручной.

**Шаги:**
1. **Сценарий 1 (защита выключена):** `unset REVSHARE_ADMIN_AUTH`, перезапустить `revshare-web`. Открыть `/admin/partners` в браузере.
2. **Сценарий 2 (защита включена):** `export REVSHARE_ADMIN_AUTH=1`, перезапустить. Открыть `/admin/partners`.

**Ожидаемый результат:**
- В сценарии 1: админка открывается сразу, без логина.
- В сценарии 2: появляется окно авторизации (Basic Auth), без правильных данных вход закрыт.
- Проверить, что выключение/включение флага реально меняет поведение (а не закэшировано).

**Открытый вопрос:** Q-04 (допустимость открытого доступа по умолчанию в целевой среде).
**Код:** `src/revshare/web.py` — middleware Basic Auth.
