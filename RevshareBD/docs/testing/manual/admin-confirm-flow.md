# Ручной сценарий: админка (admin-confirm-flow)

Пошаговая инструкция «как руками проверить админку: подтверждение отчётов, версии, события, фильтры». Один прогон занимает ~15 минут. Покрывает: A-01, A-02, A-03, A-04, A-05, A-06, A-07, A-08, A-09, A-10, A-11, A-12, A-13.

## Предусловия

- `revshare-web` и `revshare-worker` запущены.
- В БД есть минимум 4 партнёра в разных состояниях (см. шаг 1).
- Включён ли вход в админку — зависит от сценария A-13 (см. шаг 12).
- Сверочная база за текущий месяц загружена в `/admin/reconciliation-base/{period}` (если нет — A-05 и A-12 проверим отдельно).

## Подготовка тестовых данных

Самый быстрый способ — выполнить шаги 1–5 из `bot-flow.md` или `submit-flow.md` для 4 разных партнёров:

| # | Состояние | Как получить |
|---|---|---|
| 1 | Нет отчёта | Новый партнёр, ничего не загружали |
| 2 | Партнёр сдал | Загрузить через Telegram/веб, не подтверждать |
| 3 | Админ внёс вручную | `/admin/partners/{id}/report` (POST) |
| 4 | Подтверждён | Состояние 2, потом кнопка «Подтвердить» в `/reports/{id}` |

## Ход сценария

### Шаг 1. Сводка и статусы

1. Откройте `http://127.0.0.1:43127/admin/partners`.
2. Найдите 4 тестовых партнёров.

**Ожидаемо:** в колонке «Статус» — четыре разных подписи: «Не сдан», «Партнёр сдал отчёт», «Отчёт добавлен админом», «Подтверждено».

**Истории:** A-01.

---

### Шаг 2. Фильтр по статусу

1. На `/admin/partners` выберите каждый из 4 фильтров в UI.
2. Сверьте число строк.

**Ожидаемо:** каждый фильтр показывает только партнёров соответствующего статуса. Объединение всех фильтров = весь список, никто не потерян.

**Истории:** A-02.

---

### Шаг 3. Фильтр риска

1. Подготовьте партнёра с расхождением (например, неизвестный Location ID в сверочной базе).
2. Примените фильтр «риск» / «расхождение».

**Ожидаемо:** в выдаче только проблемные. Старые категории расхождений **не** показываются как статус — только как риск.

**Истории:** A-03.

---

### Шаг 4. Подтверждение партнёрского отчёта

1. Откройте `/reports/{id}` для партнёра в статусе «Партнёр сдал отчёт».
2. Нажмите «Подтвердить».
3. Проверьте статус и `status_at` (время в карточке).
4. Нажмите «Отменить подтверждение».
5. Проверьте, что статус вернулся к «Партнёр сдал отчёт» (а не к «Не сдан»).

**Ожидаемо:**
- После подтверждения — «Подтверждено», `status_at` обновлено.
- После отмены — «Партнёр сдал отчёт», `status_at` обновлено.

**Истории:** A-04.

---

### Шаг 5. Подтверждение ручного отчёта

1. Аналогично шагу 4 — но для партнёра в статусе «Отчёт добавлен админом».
2. Подтвердите, отмените.

**Ожидаемо:** после отмены возвращается «Отчёт добавлен админом», а не «Партнёр сдал отчёт».

**Истории:** A-04 (вторая ветка).

---

### Шаг 6. Перепроверка не сбрасывает подтверждение

1. Подтвердите отчёт (любой).
2. Запомните `status_at` (в карточке или через `psql`/`sqlite3`).
3. Подождите, пока `revshare-worker` сделает перепроверку (можно дёрнуть руками: `python -m revshare.worker --once`).
4. Сравните `status_at`.

**Ожидаемо:** если перепроверка не нашла изменений — `status_at` **не** сдвинулось, статус «Подтверждено».

Если нашла новое расхождение — статус остаётся «Подтверждено», но в причине появляется новое расхождение. Сброс подтверждения — **только вручную** админом.

**Истории:** A-05.

---

### Шаг 7. История отчётного месяца

1. Для партнёра с подтверждённым отчётом загрузите **новый** файл, **не подтверждайте**.
2. Откройте `/admin/partners/{id}/edit`.

**Ожидаемо:**
- В карточке партнёра отчёты показаны по месяцам.
- В выбранном месяце история содержит и неподтверждённый загруженный файл, и подтверждённые версии.
- Версия из черновика **не считается** отправленной (нет её в `/admin/partners` как «текущая»).
- После подтверждения в той же истории появляется новая версия.

**Истории:** A-06.

---

### Шаг 8. Скачивание неподтверждённого файла

1. На `/admin/partners/{id}/edit` откройте месяц с неподтверждённым файлом.
2. Нажмите «Скачать файл».

**Ожидаемо:** скачивается исходный файл. Удаление файла из админки недоступно.

**Истории:** A-06 (вспомогательно).

---

### Шаг 9. История версий

1. Подготовьте отчёт с **двумя версиями** (отправьте через бота, подтвердите, отправьте заново, подтвердите).
2. Откройте `/reports/{id}`.
3. Найдите раздел «История версий».

**Ожидаемо:** в каждой версии — оборот, валюта, число клиентов, ставка, сумма к выплате **на момент отправки**. Ставка из карточки партнёра, действовавшая тогда (даже если позже её поменяли).

**Истории:** A-07.

---

### Шаг 10. События

1. Откройте `/reports/{id}` для отчёта, внесённого вручную (из шага 5).
2. Найдите единую историю выбранного месяца.
3. Сравните с партнёрским отчётом.

**Ожидаемо:** в событиях — тип действия и исполнитель. Для ручного ввода — «админ». Для партнёрского — «отправлено», «подтверждено», «отменено». Хронологический порядок.

**Истории:** A-08.

---

### Шаг 11. Время статуса не двигается без причины

1. Возьмите подтверждённый отчёт.
2. Запомните `status_at`.
3. Запустите перепроверку (`python -m revshare.worker --once`).
4. Сравните `status_at` до и после.

**Ожидаемо:** если состояние не изменилось — `status_at` прежнее. Затем подтвердите/отмените подтверждение — `status_at` обновилось.

**Истории:** A-09.

---

### Шаг 12. Чужой статус не двигается

1. Партнёр A — подтверждённый отчёт, партнёр B — нет.
2. Запомните `status` и `status_at` партнёра A.
3. Отправьте отчёт партнёра B.
4. Сравните данные A.

**Ожидаемо:** A не изменился. Изменения у A возможны только если B прислал **тот же Location ID** (тогда появится пересечение, см. A-11).

**Истории:** A-10.

---

### Шаг 13. Пересечение Location ID

1. Партнёр A и партнёр B отправляют отчёт с **одинаковым** Location ID.
2. Откройте карточки обоих.

**Ожидаемо (после согласования Q-02):** расхождение «пересечение Location ID» видно у вовлечённых партнёров. Зафиксировать фактический результат в протоколе.

3. Повторно отправьте отчёт одного из партнёров.

**Ожидаемо:** прежняя причина у другого **не** исчезла.

**Истории:** A-11 (Q-02).

---

### Шаг 14. История при недоступных курсах

1. Подготовьте отчёт с заполненным `fx_cache` за нужный месяц.
2. Заблокируйте доступ к внешнему сервису курсов (например, `iptables -A OUTPUT -d <fx_host> -j DROP` или просто отключите Wi-Fi на время).
3. Откройте `/reports/{id}`.

**Ожидаемо:** страница открылась **без зависания**, курс подставлен из кеша, источник указан, сумма рассчитана.

4. Повторите с **пустым** `fx_cache` за нужный месяц.

**Ожидаемо:** предупреждение о fallback-курсе, страница работает.

**Истории:** A-12.

---

### Шаг 15. Basic Auth в админке

1. **Защита выключена:** `unset REVSHARE_ADMIN_AUTH`, перезапустите `revshare-web`. Откройте `/admin/partners`.

**Ожидаемо:** админка открывается сразу, без логина.

2. **Защита включена:** `export REVSHARE_ADMIN_AUTH=1`, перезапустите. Откройте `/admin/partners`.

**Ожидаемо:** появляется окно Basic Auth. С неверными данными вход закрыт.

3. Верните как было.

**Истории:** A-13 (Q-04).

---

## Что записать в протокол

| Поле | Что писать |
|---|---|
| ID сценария | `admin-confirm-flow` |
| Дата и время | когда прогоняли |
| Проверил | кто именно |
| Ветка и коммит | `git rev-parse HEAD` |
| Среда | `127.0.0.1:43127`, `REVSHARE_ADMIN_AUTH` |
| Состав данных | какие партнёры, какие состояния, реальные или тестовые |
| Доступность FX | был ли интернет к сервису курсов |
| Ограничения | что не удалось проверить и почему |

Шаблон: [`../../acceptance/run-template.md`](../../acceptance/run-template.md).
