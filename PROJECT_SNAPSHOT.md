## 1. Что за проект

**Integration Hub Revshare** — система сбора ежемесячных revshare-отчётов от партнёров Хаба Интеграций Altegio.

- Партнёр по персональной ссылке загружает Excel/CSV/PDF с оборотом, валютой, revshare и Location ID.
- Система извлекает данные, сверяет со снимком Altegio BI, показывает результат и сохраняет отчёт.
- Администратор подтверждает начисление, оборот попадает в Google-таблицу [Partnerships Altegio Revenue Accrual](https://docs.google.com/spreadsheets/d/1GoEn9TiJHMI_7YQ9LkzBnLAoKRB_PvtnootyjQAta5A/edit?gid=671431539).
- Уведомления партнёрам — через Telegram-бот и/или SMTP-почту.

**Владелец:** продуктовый лид Integration Hub Revshare (Kate). Вопросы инфраструктуры — канал `#dev-ai-coding`.

**Локальная стоимость:** `$0`. Ориентир для GCP — `$0–5/мес` при малой нагрузке, до `$20/мес` на пике. LLM-вызовы в проекте не используются.

### Что частично (🟡, 19 функций)

Главные блоки в этом статусе:

- **Telegram-бот:** привязка чата через `/start` есть, исходящие напоминания есть, но **приёма файлов (`message.document`) нет** — `src/revshare/bot.py` обрабатывает только `/start` и привязку chat_id.
- **Email:** расписание + шаблоны + исходящий SMTP есть, **входящего ящика/IMAP нет**.
- **Валидация файла:** проверяются расширение, размер и распознаваемость, но **обязательных колонок и отказа при их отсутствии нет**, заметки парсера (`turnover_not_found`, `locations_not_found`) не превращаются в блокирующие ошибки.
- **Сверка:** структурная (`store.assess`) есть — пропущенные/неизвестные/дублирующиеся ID, ставка × оборот с допуском 1%, аномалии оборота vs предыдущий месяц, построчная `verify_claim`. **Независимого оборота нет**, Impsipi Elastic не подключён.
- **Google Sheets:** `sheet_sync.py` умеет писать только оборот по партнёру/месяцу, требует ручного действия администратора. Полная автоматическая выгрузка результата сверки — нет. Service account JSON отсутствует в архиве.
- **UI админки:** глобальный месяц в шапке нет, единая карточка партнёра разнесена по страницам, нет степпера на партнёрской форме.
- **Инфраструктура:** `/health` есть, CI на `test.yml` есть, но `deploy.yml` отсутствует, логи/мониторинг/бэкапы — частично.
- **Безопасность:** Basic Auth + токен персональной ссылки есть, ролевой модели и HTTPS нет.

### Эксплуатационная готовность (⚪)

**F16 — Серверная инфраструктура 24/7:** команды запуска есть, `DEPLOY.md` есть, но шаги не отмечены, workflow деплоя отсутствует, текущая ссылка — `127.0.0.1:43127`.

### Текущее «зелёное» ядро (5 шагов)

1. Админ создаёт карточку партнёра, задаёт приложения, ставку, валюту, персональную ссылку.
2. Партнёр по ссылке загружает файл (Excel/CSV/PDF до 10 МБ).
3. `extract.parse_partner_report` извлекает суммы, валюту, Location ID и статусы; файл сохраняется в `data/uploads`.
4. `altegio_sync` подтягивает снимок Altegio BI за месяц (MySQL или MCP), если снимка ещё нет.
5. `web.py` показывает экран сверки, партнёр подтверждает, версия отчёта сохраняется, админу видна в `/reports/{id}`.

> **Критично:** «активный аккаунт» сейчас = событие в `marketplace_application_log` или платёж в BI. Это **не равно** доказанной активности по Impsipi Elastic. Снимок за месяц используется повторно без проверки свежести при новой загрузке.

## 5. Доработанные флоу

### Флоу A. Сбор отчёта через веб (основной, 🟢)

```
[Админ создаёт партнёра] → [генерируется токен]
   ↓
[Партнёр открывает /submit/{token}] → выбор месяца
   ↓
[Загрузка Excel/CSV/PDF ≤ 10 МБ] → POST /submit/{token}/parse
   ↓
[extract.parse_partner_report] → извлечение сумм, валюты, Location ID, статусов
   ↓
[altegio_sync] → если снимка месяца нет → MySQL или MCP → usage_snapshots
   ↓
[store.assess] → пропущенные ID, дубликаты, аномалии, ставка × оборот
   ↓
[Экран сверки] → партнёр видит расхождения, причины, красный/жёлтый/зелёный
   ↓
[Партнёр подтверждает] → версия отчёта сохраняется в report_versions
   ↓
[Админ в /reports/{id}] → очередь начислений → ручное подтверждение
   ↓
[sheet_sync] → запись оборота в Partnerships Altegio Revenue Accrual
```

**Локали формы:** en, uk, pl, hu, pt-BR, ru. Язык подставляется по карточке, партнёр может переключить.

### Флоу B. Уведомления партнёру (🟡, частично)

```
[Планировщик в worker.py каждый час]
   ↓
[dispatch.dispatch_for_partner] → выбирает каналы (Telegram + SMTP)
   ↓
[Telegram: bot.send_message с ссылкой на форму]
   ↓
[SMTP: email_letter + mailer.py — HTML + текстовая версия]
   ↓
[Идемпотентность: повторно то же сообщение не шлётся]
```

**Что есть:** расписание, шаблоны, отправка, защита от дублей.
**Что не работает:** SMTP не настроен локально, планировщик выключен в локальной конфигурации, реальная доставка не проверялась.

### Флоу C. Telegram-бот (🟡)

**Работает:** `/start {token}` → привязка chat_id → partner_id; `/start digest` → внутренняя сводка для админ-чата (если указан `REVSHARE_ADMIN_TELEGRAM_USER_IDS`).
**Не работает:** приём `message.document` (F01), inline-кнопки «Подтвердить», отправка результата сверки в чат.

### Флоу D. Начисления → Google Sheets (🟡)

**Работает:** страница «Начисления» — два списка («Готовы к отправке» + «Очередь записи»), ручное подтверждение, `sheet_sync.write`, статус «queued / written / failed», адрес ячейки.
**Не работает:** service account JSON отсутствует в архиве (S01), автоматическая выгрузка полного результата сверки, связь «отчёт ↔ Sheets» в карточке (UI-09).

### Флоу E. Сверка (🟡 структурная, 🔴 финансовая)

**Работает:** `store.assess` + `verify_claim` — пропущенные ID, неизвестные ID, дубликаты, ставка × оборот ±1%, аномалия оборота vs предыдущий месяц, статусы оплаты. Причины идут в `risk_score.reasons`, `display_status` (red/yellow/green).
**Не работает:** независимый оборот (R03), Impsipi Elastic (R04), кросс-партнёрское пересечение (R05).

## 7. Что мешает считать проект готовым к запуску

Из `PROJECT_STATUS.md`, без изменений:

1. Согласовать источник истины и правила сверки (что такое «Импсипи бирай», «Impsipi Elastic», что считается активностью).
2. Завершить приём файлов — Telegram `document` + email-вложения через общий безопасный конвейер.
3. Зафиксировать обязательные поля и сделать ошибки валидации блокирующими с указанием строки и колонки.
4. Замкнуть финансовую сверку — независимый оборот, валютная конвертация, явная дельта.
5. Уточнить выгрузку в Sheets — целевые поля, момент записи, идемпотентность.
6. Провести эксплуатационный запуск: публичный адрес, HTTPS, админ-доступ, SMTP, планировщик, бот, фоновые процессы, бэкапы, мониторинг, сценарий с тестовым партнёром по всем каналам.
7. Исправить тестовую изоляцию (`test_credentials_ready_requires_sheet_id` падает из-за локального `secrets.env`), затем E2E с внешними тестовыми сервисами.
